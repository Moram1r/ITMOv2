# Анализ процесса: AS IS и TO BE

## AS IS

Событие: пользователь отправляет POST `/api/reviews` с JSON `{"diff": str}`. Endpoint вызывает `review_service.review(payload["diff"])` (app/api.py:35-37). Сервис формирует prompt `"Review this pull request and find problems:\n{diff}"` и синхронно вызывает внешний `llm.generate(prompt)` (app/review_service.py:19-22). Ответ LLM как строка возвращается клиенту в поле `comment`.

Узкие места и риски:
- Отсутствует редактирование секретов в diff перед отправкой во внешний LLM (SEC-1).
- Нет ограничения размера входа и отказа 413 при >20000 символов (API-1).
- Нет таймаута внешнего вызова и контролируемого ответа при ошибках (REL-1).
- Выход не соответствует структуре OUT-1 (`summary`, `risks`, `checks` отсутствуют).
- Отсутствует наблюдаемость в виде логов request_id, длительности, статуса (OBS-1).
- Риск расширения границ: сервис мог бы делать больше, чем советовать, но это запрещено (SCOPE-1).


## TO BE

Процесс с учётом правил CASE.md: API валидирует размер и отклоняет oversize с 413; для валидных запросов сервис редактирует секреты в diff, формирует структурированный prompt, вызывает LLM с таймаутом 10с. При успехе парсит и возвращает JSON по OUT-1. При таймауте/ошибке возвращает контролируемый ответ по OUT-1 с пустыми `risks` и `checks` и `summary` с описанием деградации. В лог пишутся только `request_id`, длительность, статус. Решение оставляет последнее слово за человеком.

## Разница

| Что меняется | AS IS | TO BE | Как проверим изменение |
|---|---|---|---|
| Защита секретов (SEC-1) | Сырой diff в prompt | Редактирование секретов перед LLM | Unit: подмена diff с токеном -> [REDACTED]; снапшот prompt |
| Ограничение размера (API-1) | Принимается любой размер | 413 при >20000 символов | Integration: diff длиной 20001 -> HTTP 413 |
| Надежность LLM вызова (REL-1) | Без таймаута | Таймаут 10с и контролируемый ответ | Fault-инъекция: симулировать задержку >10с -> контролируемый JSON |
| Формат ответа (OUT-1) | {"comment": str} | {summary, risks<=3{file,line,evidence,risk}, checks[]} | Integration: happy path -> валидная схема |
| Наблюдаемость (OBS-1) | Нет логов | Логи без содержимого diff/ответа | Проверить логи: есть request_id, длительность, статус |
| Границы сервиса (SCOPE-1) | Неявно | Явно только советы, без действий | Ревью ответа: нет команд merge/approve |
