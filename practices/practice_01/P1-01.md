Findings

Critical
- app/api.py:35-38 – Missing input validation and error handling. `payload["diff"]` will raise `KeyError` if the client omits the key, resulting in a 500. Unvalidated types (non-string, huge strings) will also pass through unchecked.
- app/api.py:35-38 – No protection against prompt injection or untrusted input flowing to the LLM. The endpoint forwards arbitrary user content directly into the LLM prompt, enabling instruction hijacking and potential data exfiltration if the LLM backend has access to secrets.
- app/review_service.py:19-22 – No error handling around `llm.generate`. Any exception (timeouts, backend errors) will bubble up, causing a 500 without a meaningful error response.
- app/api.py:35-38 – Potential denial-of-service via extremely large diffs. The code builds a prompt with the entire diff and sends it to the LLM without bounding size. This risks long latencies, high LLM cost, and timeouts.
- app/api.py:35-38 – The endpoint is synchronous but triggers a potentially long-running operation (LLM call). In FastAPI, sync endpoints run in a threadpool; enough concurrent calls can exhaust worker threads and degrade the service.

Major
- app/api.py:35-38 – Request/response are untyped dicts. FastAPI will allow any JSON object. There’s no schema or automatic 422 validation. Use Pydantic models to define and validate input/output.
- app/review_service.py:19-22 – The LLM prompt is unstructured. Returning a free-form single “comment” field makes it hard for clients to consume predictably. Consider a structured response (e.g., list of findings with severities/locations).
- app/review_service.py:19 – No truncation or normalization of diff before embedding in the prompt. Even aside from DoS, this risks exceeding LLM token limits and getting truncated mid-thought.
- app/review_service.py:9-13 – Changing the `Protocol` method body to a multi-line with `...` is harmless, but it signals implementation where only a signature is required. Keep interface stubs minimal for clarity.

Minor
- app/api.py:35-38 – Prefer explicit response model and status codes for better OpenAPI docs. Currently, clients won’t get a clear contract.
- app/api.py:35-38 – Consider `async def` for the route and an async LLM client if supported. If the LLM client is sync-only, document that the call is CPU-bound vs IO-bound and ensure threadpool settings are appropriate.
- app/review_service.py:19-22 – The prompt could benefit from delimiters and explicit instructions to ignore any instructions present in the diff for safer and more consistent outputs.
- Typing – `dict[str, str]` requires Python 3.9+. If the project targets 3.8, this will break runtime. Confirm the target Python version.

Open Questions
1. What Python version(s) does the project target? If 3.8, we need `Dict[str, str]` or `from __future__ import annotations`.
2. What error semantics should the API expose when `diff` is missing or invalid? 400 vs 422, and what error format do clients expect?
3. Are there size constraints or cost limits for LLM requests we need to enforce?
4. Should the response be a single comment or a structured list of issues (severity, file, line) for downstream automation?
5. Does the LLM client support async? If so, do we want to convert the endpoint to async to avoid threadpool exhaustion?
