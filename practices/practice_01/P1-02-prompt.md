1. Цель и роль
- Цель: подготовить связный комплект артефактов для AI‑reviewer
- Роль AI: Архитектор SDLC, собирающий продуктовый и технический контекст, формулирующий проблему и метрики, описывающий процессы AS IS/TO BE, готовящий ADR, план поставки и проверяемые тесты.
2. Входы и источники
- Обязательные входы:
    - practices/practice_01/TRAINING_PR.diff
    - practices/practice_01/CASE.md
- Запрещено использовать web, внешние источники или домыслы. Использовать только информацию из данных файлов и общие требования шаблонов.
3. Задача и артефакты
- Использовать материалы CASE.md для Context Pack и правил (SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1).
- Что сделать: заполнить следующие файлы целиком, соблюдая их структуру и весь контекст:
    - practices/practice_01/context.md
    - practices/practice_01/problem.md
    - practices/practice_01/analysis.md
    - practices/practice_01/product_management.md
    - practices/practice_01/project_management.md
    - practices/practice_01/adr.md
    - practices/practice_01/tests_unit.md
    - practices/practice_01/tests_integration.md
    - practices/practice_01/tests_load.md
    - practices/practice_01/tests_e2e.md    
- Не трогать: practices/practice_01/prompts.md, practices/practice01/CASE.md, practices/practice01/P1-01.md, README.md, TRAINING_PR.diff, Makefile, PDF.
4. Формат результата
- Язык: русский, инженерный нейтральный тон, конкретные формулировки.
- Разметка: GitHub‑flavored Markdown; избегать вложенных списков; сохранять структуру таблиц и заголовков из шаблонов файлов.
- Кодировки: только ASCII.
- В context.md/Context Pack переносить только релевантные правила из CASE.md; явно не включать нерелевантные (snake_case для БД, i18n для фронтенда). 
5. Полномочия и запреты
- Разрешено:
    - читать входные файлы
    - извлекать факты/правила формулировать измеримые метрики и проверяемые тесты
    - давать краткие пояснения, где это повышает проверяемость.
- Запрещено: 
    - Писать в разделах «Как использовали AI»
    - Выдумывать факты вне материалов или противоречащие им.
    - Добавлять новые файлы/изображения/зависимости.
    - Изменять prompts.md и CASE.md.
    - Давать общие советы без evidence или безотносительно кейса.
    - Насыщать лишней теорией — придерживаться задач шаблонов.
6. Рабочий процесс и остановка
- Шаги:
1. Прочитать TRAINING_PR.diff, зафиксировать текущее состояние проекта.
2. Соберите Context Pack: релевантные правила (SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1), формат входа/выхода, хорошие/плохие примеры, ограничения. Исключите нерелевантные пункты из CASE.md.
4. Заполните файлы в следующем порядке, поддерживая согласованность: context.md → problem.md → analysis.md → product_management.md → project_management.md → adr.md → tests_*.
5. Для каждого файла выполните самопроверку по критериям из раздела 7.
6. Остановитесь, когда все критерии Definition of Done выполнены.
7. Проверки и evidence
- Согласованность:
    - Пользователь/роль и проблема в problem.md совпадают с контекстом в context.md.
    - Метрики в problem.md измеримы и соотносятся с правилами из CASE.md.
    - TO BE в analysis.md прямо решает узкие места AS IS и соотносится с метриками.
    - Use case и user stories проверяемы и непротиворечивы; acceptance criteria конкретны.
    - План поставки отражает инкременты, роли человека/AI, проверки и зависимости.
    - ADR содержит контекст, решение, альтернативы и главный риск с проверкой.
    - tests_unit/tests_integration/tests_load/tests_e2e покрывают требования OUT-1, REL-1, API-1, SEC-1, QA-1; у каждого теста есть наблюдаемые критерии и источники evidence.
- Evidence:
    - Ссылки на файлы/строки diff в рисках и проверках, когда применимо.
    - Для нагрузочных и интеграционных — чёткие пределы (latency/коды/проценты), откуда берём данные (логи по OBS-1, отчёты CI).
8. Definition of Done
- Все целевые файлы полностью заполнены по структуре шаблонов без пустых разделов, кроме «Как использовали AI».
- В context.md оформлен Context Pack с релевантными правилами, форматами и ограничениями; нерелевантные правила из CASE.md не включены.
- В problem.md определены пользователь, ситуация, текущие проблемы, границы; добавлены 4–6 измеримых метрик, соответствующих кейсу и правилам.
- analysis.md содержит AS IS и TO BE , таблицу «Разница» с проверками.
- product_management.md: один рабочий сценарий, таблица use case, 2 user stories (позитивная и граничная) с чёткими acceptance criteria.
- project_management.md: 2–3 инкремента с ролями человека/AI, проверками и зависимостями; диаграмма Ганта с корректными диапазонами.
- adr.md: статус, дата, ответственные; контекст; решение; минимум 2 альтернативы с причинами отказа; последствия и главный риск с планом проверки; актуализированная схема.
- tests_unit.md: минимум 3 кейса (валидация/лимиты/обработка ошибок), с входом, ожидаемым результатом и evidence.
- tests_integration.md: минимум 2 сценария (happy path, oversize 413) с воспроизводимостью и evidence.
- tests_load.md: минимум 4 сценария (стабильная нагрузка, пик, oversize‑флуд, fault‑инъекция таймаутов) с пределами и источниками метрик.
- tests_e2e.md: позитивный, негативный, граничный сценарии с наблюдаемым результатом и evidence.
- В каждом файле раздел «Как использовали AI» заполнен кратко и по делу, ссылка на prompts.md указана или помечена как «будет добавлена».
- Стиль: русский, без вложенных списков, ASCII, без лишней теории, только проверяемые утверждения.
- Нет противоречий между файлами; правила из CASE.md применены последовательно.
Подсказки по файлам (что должно быть внутри)
- context.md:
    - «Продукт и команда сейчас»: кратко AS IS по кейсу AI‑ревьюера PR.
    - Context Pack: факты и правила (SEC-1, API-1, REL-1, OUT-1, SCOPE-1, QA-1, OBS-1), формат входа/результата, ограничения/запреты, хороший/плохой пример из CASE.md, что неизвестно.
- problem.md:
    - Пользователь, ситуация, что происходит сейчас; почему мешает; что не входит.
    - Метрики, связанные с OUT-1, REL-1, API-1, SEC-1, OBS-1; когда и как мерить.
    - Почему метрики подтверждают решение проблемы.
- analysis.md:
    - AS IS: от события до результата с задержками и ручными шагами.
    - TO BE: простой процесс с участием AI и проверкой человеком; Mermaid‑схема.
    - Таблица «Разница» с методами проверки изменений.
- product_management.md:
    - Первый рабочий сценарий в одной фразе.
    - Use case таблица (Актор/Триггер/Предусловия/Результат/Отказ).
    - 2 user stories с Given/When/Then, позитивная и граничная.
- project_management.md:
    - 2–3 инкремента с ролями человека/AI и проверками.
    - Диаграмма Ганта с разумными датами.
- adr.md:
    - Контекст (кейc, ограничения, формат).
    - Решение: структура ответа, ограничения и обработка ошибок/лимитов.
    - Альтернативы: например, «свободный текст без структуры», «синхронный вызов без таймаутов», «игнорировать SEC-1/API-1» и почему отклонено.
    - Последствия, ограничения, главный риск и способ проверки.
    - Схема потока: вход → сервис → LLM → проверка человеком → результат, с пометками про SEC-1/API-1/REL-1/OUT-1.
- tests_unit.md:
    - Проверки форматирования prompt, редактирования секретов (SEC-1), обработки исключений (REL-1), лимитов размера (если на уровне сервиса).
- tests_integration.md:
    - /api/reviews: валидный diff → структурированный ответ (OUT-1), oversize diff → 413 (API-1), симуляция таймаута → контролируемый ответ (REL-1).
- tests_load.md:
    - Нагрузочные сценарии с пределами p95, error rate, 413 отказ, fault‑инъекция таймаутов; источники evidence (логи OBS-1/отчёты CI).
- tests_e2e.md:
    - Сценарии пользователя: позитивный, негативный, граничный, с наблюдаемыми результатами.
