# Проблема и метрики

## Проблема

 - Пользователь: разработчик/ревьюер, использующий сервис AI-помощника для анализа PR.
- Ситуация: в репозитории добавлен endpoint `/api/reviews`, который принимает `diff` и через `ReviewService` отправляет его во внешний LLM, возвращая строковый комментарий.
 - Что происходит сейчас: реализация нарушает правила CASE.md - нет редактирования секретов (SEC-1), нет ограничения размера и ответа 413 (API-1), нет таймаута и контролируемого ответа (REL-1), формат ответа не соответствует OUT-1, отсутствуют наблюдения по OBS-1, а сервисные границы по SCOPE-1 не закреплены в ответе.
 - Почему это мешает пользователю или бизнесу: повышенные риски утечки секретов, нестабильность и подвисания при длинных запросах, невозможность автоматической проверки результата из-за нестандартизированного выхода, отсутствие операционных метрик затрудняет разбор инцидентов.
- Что не входит в задачу: изменение логики ревью, работа с БД и схемами, интернационализация фронтенда, любые действия в GitHub (approve/merge), интеграции вне описанного сервиса.

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля ответов в формате OUT-1 | 0%; парсим поля `summary`, `risks[]`, `checks[]` | >= 95% корректных ответов | на каждом успешном вызове | HTTP ответы сервиса |
| Доля отказов 413 на oversize (>20000 симв.) | 0%; отправить diff длиной 20001 | 100% запросов возвращают 413 | при интеграционном тесте | HTTP статус и тело ответа |
| p95 времени ответа при валидном diff | не определено; измеряем end-to-end | <= 2.0 c при успешном ответе | в нагрузочных тестах | OBS-1 логи: длительность, отчеты CI |
| Доля таймаутов LLM, превращённых в контролируемый ответ | 0%; симуляция timeout >10c | 100% таймаутов дают контролируемый JSON по OUT-1 | при fault-инъекциях | HTTP ответы + логи статуса |
| Доля редактирования секретов в prompt | 0%; diff с токеном -> [REDACTED] | 100% секретов редактируются | на unit/integration | снапшоты сформированного prompt |

## Почему изменение метрики подтвердит решение проблемы
Метрики напрямую отражают соблюдение правил: формат ответа (OUT-1), отказ по размеру (API-1), контролируемая деградация при таймауте (REL-1), редактирование секретов (SEC-1), а p95 подтверждает эксплуатационную пригодность при сохранении наблюдаемости (OBS-1). Достижение целевых значений снижает риски утечки, повышает предсказуемость SLA и позволяет автоматизировать проверку результатов.
