# Спецификация логики графа C#-проекта — версия «после»

**Статус:** согласована с командой UI. Источник истины по типам, API, лимитам
и состояниям — `contract.md` (решения раздела 11 подтверждены 2026-10-28).
Здесь требования к вычислению графа; экраны не проектируются.

## 1. Вход и отбор

Вход: `File` (ZIP) и готовый `AnalysisResult` от `analyzeZipFile`.

Читаются только записи:

- не каталоги, расширение `.cs` или `.csproj` без учёта регистра;
- вне `obj/` и `bin/` на любом уровне;
- с безопасным нормализованным путём (без абсолютных путей, диска, `..` за корень).

Остальное не открывается: `.sln`, `.props`, `.targets`, `.json`, `.env`, ключи,
сертификаты и прочие типы. `obj/`, `bin/` и другие типы попадают только
в `stats.excluded`. Файлы с небезопасным путём (абсолютный, диск, `..` за
корень) не читаются и входят в `stats.excluded.otherTypes`.

## 2. Модель данных

Согласно `contract.md`, раздел 4:

- узлы: `ProjectNode`, `SourceFileNode`, `ExternalPackageNode`;
- рёбра: `GraphEdge` с `kind` (`project-reference`, `package-reference`, `using`)
  и `certainty` (`declared`, `namespace-match`, `conditional`);
- неразрешённые ссылки: `UnresolvedItem` — отдельный список, не рёбра;
- результат: `GraphResult` с `nodes`, `edges`, `unresolved`, `stats`, `warnings`;
- `tablePath` — исходная строка из `AnalysisResult.files`, у которой
  нормализованный путь совпадает с `path`, или `null`;
- идентификаторы и порядок детерминированы и не зависят от локали.

Направление ребра: `from` — зависимый, `to` — зависимость.

## 3. Правила зависимостей

### `.csproj`

- `ProjectReference` → ребро `project-reference` (`declared`).
- `ProjectReference Include` разрешается относительно каталога проекта;
  небезопасный путь → `unresolved` `PROJECT_NOT_FOUND`.
- `PackageReference` → ребро `package-reference` (`declared`), версия в
  `packageVersion`.
- Ссылки внутри `Condition` или `Choose/When` → `certainty: 'conditional'`
  с условием; вложенные условия объединяются через ` && ` от внешнего
  к внутреннему.
- XML-комментарии в `.csproj` игнорируются и не создают ссылок.
- Один пакет — один узел, все встреченные версии — в `versions`.
- Проект без `.csproj` не создаётся; `.sln` не анализируется.

### `.cs`

- `using Namespace;` и `global using` разбираются статически, без Roslyn и без
  семантического анализа; `#if` не вычисляется, using внутри всех ветвей
  считаются присутствующими, условность поддерживается только для `.csproj`.
- `.cs` привязывается к ближайшему `.csproj` вверх по каталогам; при нескольких
  кандидатах выбирается первый по побайтовому порядку и добавляется
  `MULTIPLE_PROJECTS_IN_DIR`.
- `using` сопоставляется с файлами, объявившими namespace, **с учётом регистра**;
  точное совпадение даёт ребро `using` / `namespace-match`.
- Несколько файлов объявляют один и тот же namespace — это не ошибка; рёбра
  идут к каждому другому файлу, неоднозначности нет. Если namespace объявлен
  в самом файле-источнике, ссылка не создаёт рёбер.
- Точного совпадения нет, но есть совпадение в другом регистре → `unresolved`
  с `NAMESPACE_CASE_MISMATCH` и кандидатами, без ребра.
- Точного совпадения нет, но есть объявленные namespace с этим префиксом →
  `unresolved` с `NAMESPACE_NOT_FOUND` и кандидатами, без ребра.
- Внешний namespace без файла в архиве → `unresolved` с `EXTERNAL_NAMESPACE`.
- `using static` не создаёт ребра и даёт `STATIC_USING_UNSUPPORTED`, кроме
  `System`/`System.*`; кандидаты — объявленные namespace-префиксы цели,
  от длинного к короткому.
- Alias (`using X = A.B;`) даёт ребро только при точном совпадении `A.B`
  с объявленным namespace; иначе `ALIAS_TARGET_UNSUPPORTED` (кроме
  `System`/`System.*`) с такими же кандидатами.
- `System` и `System.*` не создают ни рёбер, ни `unresolved`; учитываются
  в `stats.systemUsingCount`, включая static и alias.
- Пути нормализуются без учёта регистра, `\` и `/` считаются эквивалентными;
  namespace так не нормализуется.
- Повторные `using` не создают дубликатов рёбер; у неразрешённых ссылок
  повторы агрегируются, `count` — число вхождений.
- `using` на namespace, объявленный в том же файле, не создаёт рёбер ни к одному
  файлу и не попадает в `unresolved`; ребро файла к самому себе также
  не создаётся.
- Циклы допустимы, отдельно не помечаются.
- Неразрешённые ссылки не создают фиктивных узлов и рёбер.
- Граф содержит только прямые связи; глубина анализа — 1, рекурсивного обхода
  зависимостей нет.

## 4. Что не входит в MVP

Roslyn, компиляция, выполнение кода, reflection, DI, анализ тел методов и типов,
динамические зависимости, препроцессорные условия `#if` в `.cs`, алиасы
`tsconfig`-подобных конфигураций, `.sln`, построение графа по `obj/`-артефактам,
отмена и прогресс в процентах.

## 5. Лимиты

Существующие лимиты ZIP не меняются: 20 МиБ, 2000 записей, 100 МиБ.

Лимиты графа:

| Лимит | Значение | Поведение |
| --- | ---: | --- |
| `maxFileBytes` | 1 МиБ | файл не читается, узел `unknown`, предупреждение |
| `maxTextBytes` | 20 МиБ (UTF-8 байты) | `LIMIT_TEXT_BYTES`, граф не возвращается |
| `maxNodes` | 3000 | `LIMIT_NODES` |
| `maxEdges` | 10 000 | `LIMIT_EDGES` |

Частичный граф не маскирует превышение жёсткого лимита.

## 6. API и ошибки

```ts
analyzeZipFile(file, limits?)            // не меняется
analyzeCsharpGraph(file, analysis, limits?): Promise<GraphResult>
analyzeProjectZip(file, limits?)         // необязательная обёртка, UI не использует
GRAPH_LIMITS: GraphLimits
```

- `analyzeCsharpGraph` — чистая относительно входа: не меняет `file` и `analysis`,
  не трогает DOM, не ходит в сеть.
- `GraphAnalysisError` содержит `code`, `limit`, `actual`, `limitName` и готовый
  русский `message`; коды: `NO_CSHARP_FILES`, `LIMIT_TEXT_BYTES`, `LIMIT_NODES`,
  `LIMIT_EDGES`, `INPUT_MISMATCH`.
- Ошибка отдельного файла не роняет граф: узел `unknown` + `GraphWarning`.
- `warnings[].message` и `UnresolvedItem.message` — готовые строки без фрагментов
  кода и секретов.
- В результате нет исходного текста, литералов и HTML.

## 7. Безопасность и производительность

- Загруженный код не выполняется и не импортируется; нет `eval`/`new Function`.
- `.env`, ключи и сертификаты не читаются.
- Текст `.cs`/`.csproj` декодируется как UTF-8; недопустимые последовательности
  заменяются, отдельного определения бинарности нет.
- Один проход по ZIP, ранний выход при превышении жёстких лимитов.
- Повторный вызов на том же ZIP и лимитах даёт структурно одинаковый результат.

## 8. Условия приёмки

1. ZIP с `A/A.csproj` → `B/B.csproj` и `using B.Services` даёт ожидаемые узлы и
   рёбра; направление «зависит от»; счётчики совпадают с массивами.
2. Несуществующий `ProjectReference`, внешний namespace и namespace в другом
   регистре дают `unresolved`, `stats.unresolvedCount` равен сумме `count`,
   фиктивных рёбер нет.
3. Условные ссылки помечены `conditional` и содержат `condition`; `using static`
   и алиасы без точного namespace не дают рёбер; циклы не ломают результат;
   один пакет — один узел с массивом версий.
4. Файл больше 1 МиБ → `unknown` + предупреждение; превышение текста, узлов или
   рёбер → `GraphAnalysisError` с `limit` и `actual`.
5. `obj/`, `bin/`, `.sln`, `.env` не читаются; два запуска дают одинаковый
   `GraphResult`; `analyzeZipFile` проходит прежние тесты.

## 9. Что сохраняется

`analyzeZipFile`, `AnalysisResult`, `ZipEntryInfo`, `ZipAnalysisError`, `LIMITS`,
`formatBytes` и их поведение не меняются. Новый код добавляется отдельным слоем
и не ломает существующие импорты.
